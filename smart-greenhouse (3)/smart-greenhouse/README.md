# Умная теплица: распределённая микроконтроллерная система

> **Пошаговая инструкция для запуска (Docker, Wokwi, ноутбук, скриншоты, план защиты): [docs/ИНСТРУКЦИЯ.md](docs/ИНСТРУКЦИЯ.md).**

Проект по курсу «Анализ больших данных при моделировании сложно-структурированных систем».
Три виртуальных ESP32 (Wokwi) измеряют и регулируют параметры теплицы, обмениваются данными по **MQTT**, backend
(**FastAPI + TimescaleDB**) хранит телеметрию и события, считает аналитику, применяет правила и отдаёт API; мониторинг —
**Grafana/Prometheus** и встроенный web UI; анализ данных — Jupyter-ноутбук.

| Узел | Что делает | Новые датчики / исполнители |
|---|---|---|
| `gh-soil-01` | полив: гистерезис по влажности почвы, защита насоса | датчик влажности почвы, реле насоса |
| `gh-tank-01` | контроль запаса воды, сигнализация | ультразвуковой HC-SR04, зуммер, светодиод |
| `gh-climate-01` | климат: проветривание и досветка | NTC-термистор, фоторезистор, сервопривод форточки, светодиод |

Подробно о формате сообщений, надёжности и REST API: [docs/PROTOCOL.md](docs/PROTOCOL.md).

## 1. Что нужно установить

* Docker Desktop (Compose v2) — для backend, БД, Grafana.
* Python 3.10+ — только для тестов, генерации датасета и ноутбука (`pip install pandas numpy matplotlib scikit-learn scipy`).
* Аккаунт на [wokwi.com](https://wokwi.com) (бесплатный) — для виртуальных устройств. Нужен один из двух режимов, см. ниже.

## 2. Быстрый старт

### Вариант А. Без Wokwi: локальный симулятор (самый простой, проверьте им систему первой)

```bash
cp .env.example .env            # (Windows PowerShell: copy .env.example .env) и задайте пароли
docker compose --profile sim up -d --build
```

Через 30–60 секунд:

| Что | Адрес |
|---|---|
| Web UI (устройства, графики, управление) | http://localhost:8000/ui |
| Swagger / API | http://localhost:8000/docs |
| Grafana (логин `admin`, пароль из `.env`) | http://localhost:3000 → Dashboards → Greenhouse → «Умная теплица» |
| Prometheus | http://localhost:9090 |

Ключ API (`API_KEY` из `.env`) нужно ввести в Web UI при первом открытии. Симулятор работает в ускоренном режиме
(почва сохнет быстрее, температура меняется быстрее), поэтому полив, тревоги и реакции видны за минуты.

### Вариант Б. С виртуальными ESP32 в Wokwi (то, чего требует задание)

Wokwi работает в облаке и ходит на публичный MQTT-брокер, поэтому backend должен слушать **тот же** брокер.

1. Придумайте уникальный префикс топиков (публичный брокер общий для всех!):
   `python tools/set_topic_root.py my-team-42/greenhouse`
2. В `.env` поставьте `MQTT_HOST=broker.hivemq.com` и запустите `docker compose up -d --build`
   (без `--profile sim`).
3. Для каждого из трёх узлов создайте на wokwi.com проект **ESP32** (Arduino) и заполните его файлами из
   `firmware/<узел>/`: `sketch.ino`, `gh_common.h`, `gh_logic.h` (создайте как новые файлы вкладкой «+»),
   `diagram.json` и `libraries.txt` (вставьте содержимое в одноимённые вкладки). Папки:
   `firmware/gh-soil-01`, `firmware/gh-tank-01`, `firmware/gh-climate-01`.
4. Нажмите ▶ у каждого проекта. В Serial Monitor появится подключение к Wi-Fi `Wokwi-GUEST`, к брокеру и NTP.
   Через несколько секунд узлы появятся в Web UI со статусом `online`.
5. Управляйте физикой в Wokwi: ползунок влажности почвы, расстояние на HC-SR04, температура NTC и освещённость
   фоторезистора. Например: опустите ползунок влажности ниже 30 % — включится насос; увеличьте расстояние на
   HC-SR04 до 90+ см — «бак почти пуст», насос заблокируется и придёт тревога.
6. Остановка: `docker compose down` (данные сохраняются в томах; `docker compose down -v` — полная очистка).

> Если узел не появляется: проверьте, что `TOPIC_ROOT` в `.env` и `GH_TOPIC_ROOT` в `gh_common.h` совпадают
> и что `MQTT_HOST=broker.hivemq.com`. Публичный брокер иногда недоступен — тогда используйте вариант А.

## 3. Сценарии для демонстрации

| Сценарий | Как вызвать | Что должно произойти |
|---|---|---|
| Штатная работа | ничего не делать | автоматический полив при влажности < 30 %, до 60 % |
| Ручное управление | UI или `POST /api/v1/devices/gh-soil-01/commands` `{"cmd":"pump_on","duration_s":10}` | узел подтверждает `ack`, насос работает ≤ 10 с |
| Удалённая настройка | `PUT /api/v1/devices/gh-soil-01/config` `{"moist_low":40}` | `config/ack`, новые пороги, сохраняются после перезапуска |
| Пустой бак | уровень в `gh-tank-01` ≤ 10 % | `tank_state` critical, зуммер, насос блокируется правилом backend |
| Жара | температура > 35 °C | `heat_alarm`, backend сам отправляет `vent_open` |
| Обрыв связи | остановить/запустить узел | `device_offline` (LWT), после возврата — `device_online`, буфер дошёл с `buf=1` |
| Отказ датчика | отключить/«заглушить» HC-SR04 | `sensor_fault`, затем `sensor_recovered` |
| Отказ насоса | насос включён, влажность не растёт | `irrigation_ineffective` → `pump_fault` → блокировка |

## 4. Тесты и проверка (запускаются без Docker)

```bash
bash firmware/tests/run_tests.sh                       # прошивки: юнит-тесты логики + сценарии скетчей на хосте (g++)
cd backend && pip install -r requirements-dev.txt \
  && python -m unittest discover -s tests -t . -v      # backend: протокол, движок, сервис, контракт, замкнутый цикл, API
python tools/sync_firmware.py --check                  # общие файлы прошивок в папках узлов не разошлись
python simulator/make_dataset.py --out /tmp/ds         # детерминированный датасет (должен совпасть с data/)
```

Что покрыто: обе стороны протокола (контрактный тест воспроизводит реальные логи прошивок), последовательности
`seq`, дубликаты команд, буферизация, LWT, правила, замкнутый цикл «устройства ↔ backend» на 72 ч с 9 сценариями.
Те же проверки выполняет CI (`.github/workflows/ci.yml`).

## 5. Данные и анализ

* `data/telemetry.csv`, `data/events.csv`, `data/commands.csv` — 72 часа работы (15 710 строк телеметрии,
  48 событий, 3 команды). Получены тем же кодом backend, что и в боевом режиме (`simulator/make_dataset.py`,
  seed 7, воспроизводятся побайтно).
* `notebooks/analysis.ipynb` — анализ: качество данных, эффективность полива, адаптивная частота, буферизация,
  инциденты, аномалии (IsolationForest против правил backend), суточная сводка. Уже выполнен; пересобрать:
  `python tools/build_notebook.py` (либо открыть в Jupyter → Restart & Run All).
* Реальные данные из работающей системы: `GET /api/v1/export/telemetry.csv`.

## 6. Структура репозитория

```
firmware/        прошивки трёх узлов (+ shared/ — общий код, tests/ — хост-тесты со стабами Arduino)
backend/         FastAPI-сервис, схема БД, тесты, Dockerfile
simulator/       модель теплицы и узлов; make_dataset.py (офлайн), run_mqtt.py (к настоящему брокеру)
infra/           Mosquitto, Prometheus, Grafana (датасорсы и дашборд)
data/            датасет (CSV)
notebooks/       Jupyter-анализ
docs/            PROTOCOL.md (формат сообщений, API, правила), отчёт, презентация
tools/           gen_wokwi.py, sync_firmware.py, set_topic_root.py, build_notebook.py
docker-compose.yml, .env.example, .github/workflows/ci.yml
```

Правка общего кода прошивок: редактируйте только `firmware/shared/*`, затем `python tools/sync_firmware.py`
(копирует в папки узлов, чтобы каждый Wokwi-проект был самодостаточным).

| Требование | Где реализовано |
|---|---|
| ≥ 3 виртуальных ESP32 в Wokwi | `firmware/gh-soil-01`, `gh-tank-01`, `gh-climate-01` (скетч + `diagram.json`) |
| ≥ 2 новых типа датчиков | влажность почвы, HC-SR04, NTC-термистор, фоторезистор (+ исполнители: насос, форточка, зуммер) |
| Протокол, метки времени, seq | MQTT QoS 1, JSON v1, `ts` (NTP, мс), `boot`+`seq` — [docs/PROTOCOL.md](docs/PROTOCOL.md) |
| Телеметрия и управление | `telemetry`, `cmd`/`cmd/ack`, `config`/`config/ack` |
| Штатный режим + ≥ 1 доп. сценарий | 9 сценариев: жара, утечка, обрыв связи, отказ датчика, отказ насоса и др. |
| Backend с API | `backend/app`, REST `/api/v1`, Swagger `/docs`, web UI `/ui` |
| Центральное хранилище | TimescaleDB: `telemetry` (гипертаблица), `events`, `commands`, `devices` |
| Мониторинг и визуализация | Grafana-дашборд, Prometheus `/metrics`, web UI |
| Контейнеризация | `docker-compose.yml` (6 сервисов, healthchecks), `backend/Dockerfile` |
| Jupyter-анализ | `notebooks/analysis.ipynb` |
| Прикладная логика | блокировка насоса, авто-проветривание, детекторы утечки/аномалий/«залипания» |
| ≥ 2 новые технологии | см. ниже |
| Диагностика, ошибки, восстановление | LWT+heartbeat, watchdog, авто-reboot, повтор конфигурации, буфер, безопасный режим |
| Воспроизводимое развёртывание, автопроверки | compose + `.env`, CI, 42 теста backend, хост-тесты прошивок |

**Новые технологии, решающие конкретные задачи проекта:** TimescaleDB (хранение и `time_bucket`-агрегаты временных
рядов), MQTT LWT + retained-heartbeat (обнаружение отказа узла без опроса), удалённая версионируемая конфигурация с
подтверждением (настройка без перепрошивки), адаптивная частота телеметрии (экономия трафика), кольцевая буферизация
(нет потерь при обрыве), онлайн-детектор аномалий (EWMA z-score), Prometheus + Grafana, ограничение частоты и
API-ключ, Telegram-уведомления (задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env`).

## 8. Безопасность и ограничения

* Для учебного стенда брокер Mosquitto разрешает анонимный доступ, а Wokwi использует публичный брокер без
  авторизации — не отправляйте через него ничего конфиденциального. Для реального применения включите
  `password_file` и TLS в `infra/mosquitto/mosquitto.conf`.
* Сменяйте `API_KEY` и пароли в `.env`; значения по умолчанию годятся только для демонстрации.
* Датасет синтетический (физическая модель + шум); пороги нужно калибровать на реальной теплице.
* Бесплатный Wokwi может ограничивать длительность непрерывной симуляции — если узел остановился, просто запустите его снова.
